# F-002 · Sensores Bluetooth visibles en tiempo real (2026-10-02)

## Área
F — Recepción Bluetooth y compatibilidad con el prototipo existente.

## Diagnóstico
La captura del teléfono muestra «Revisa el dato ESTADO» y todos los sensores
vacíos. El parser trataba `ESTADO` e ICA del equipo como datos obligatorios para
la validez de la lectura. El firmware histórico documentado emite `ESTADO`
textual; una reproducción con `ESTADO:EXCELENTE` genera ese mismo bloqueo.
Además, la pantalla usaba la validación del análisis para mostrar cualquier
sensor, por lo que un solo campo inválido escondía todos los valores.

## Implementación
`ESTADO` e ICA auxiliares ilegibles o duplicados se convierten en avisos; no
afectan sensores ni deciden permisos de agua. Los errores de sensores y de
versión de protocolo conservan su validación. La pantalla usa la última trama
reciente para mostrar valores aunque haya errores en otro campo, sin esperar
estabilidad/calibración. El análisis sigue exigiendo una trama íntegra reciente.
Curvas independientes de hasta 60 tramas muestran evolución, sin unir valores
inválidos ni interrupciones. Se añade diagnóstico con hora y trama textual.
DEMO emite valores variables y estado textual para comprobar el caso histórico.

## Riesgo y control
Mostrar números no los convierte en mediciones exactas ni en agua consumible.
Se separa el monitoreo del análisis, se mantienen errores visibles y se retiran
datos de la vista actual tras cinco segundos o desconexión. No se mezclan campos
de distintas tramas para capturar. S1–S8 conservadas; motor 0.3.0 sin cambios.

## Verificación
61 pruebas aprobadas y TypeScript correcto; cobertura del motor 100 %. Casos
regresión: estado textual, ICA auxiliar inválido, versión ilegible, sensor
ausente, lecturas cambiantes, historial limitado, datos antiguos y cortes de
curva. El guion del doc 13 incluye estos casos.

APK 0.3.1 con `versionCode:4`: build release y lint vital aprobados;
52 008 938 bytes; paquete `co.refluye.campo`, mínimo API 24, objetivo 36 y
cuatro ABI (arm64-v8a, armeabi-v7a, x86, x86_64). Firma v2 verificada con el mismo
certificado de 0.3.0 (`fac61745dc0903786fb9ede62a962b399f7348f0bb6f899b8332667591033b9c`).
SHA-256 de APK y archivo `.sha256` coinciden:
`c0a30f4bd12f2e2ff6488df3315901787f9bfee0045322660acf59abce79c8d9`.
El build usa Kotlin sin compilación incremental y dentro del proceso de Gradle
para evitar los errores del daemon con rutas C:/R: de la compilación anterior.

Prueba física intentada: Windows detecta Redmi 13 como dispositivo WPD con
problema código 10; ADB no enumera el teléfono. El usuario confirma que el USB
del prototipo solo alimenta y solicita probar manualmente por Bluetooth con la
APK nueva. No se afirma recepción física verificada. La falla reproducida con
estado textual queda cubierta; la trama exacta del prototipo se podrá revisar
en el panel nuevo si persiste algún problema.

y la reproducción del protocolo, no la recepción del dispositivo físico.
